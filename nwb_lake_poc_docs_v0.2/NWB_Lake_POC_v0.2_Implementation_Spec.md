# NWB-Lake Portable Data Packet Specification, v0.2

## Status of this document

This document set specifies the NWB-Lake proof-of-principle data packet. It is v0.1 with revisions R1–R41 and R43–R70 applied. R42 was withdrawn.

The revision documents in `revisions/` remain the record of why each requirement holds. This specification states only what holds. A requirement introduced or changed by a revision cites it as `(R<N> §<clause>)`; an uncited requirement is unchanged from v0.1.

The specification is versioned independently of the identifiers a packet records. See §5.

## 1. Scope

### 1.1 Purpose

This specification defines a portable representation of extracellular electrophysiology data as a small semantic and logical standard over commodity storage formats. It defines:

- a semantic standard: the meaning of the concepts represented (Part 01);
- a logical standard: those concepts as computable resources (Part 02);
- a physical profile: how those resources are stored (Part 03);
- a packet catalog binding the resources of one bundle (Part 04);
- a validation-first import procedure (Part 05).

### 1.2 Out of scope

This specification does not define a storage engine, an object model compatible with PyNWB, an NWB exporter, a distributed compute model, or ontology machinery. It has no runtime dependency on NWB, HDMF, or PyNWB.

A compatibility projection into NWB is deferred and is not required for conformance.

### 1.3 Applicability

The design goal is to test whether neurophysiology data can be represented over commodity substrates: Parquet for tables, Zarr for dense arrays, standard media containers for media, and JSON for the catalog. **NWB-Lake** is a placeholder name.

## 2. Conformance

### 2.1 Conformance targets

Requirements in this specification apply to four classes of implementation. Each requirement states or implies which.

| target | definition |
|---|---|
| **writer** | produces a packet from source data |
| **reader** | opens a packet and resolves its resources |
| **validator** | decides whether a packet conforms |
| **consumer** | interprets values a reader returns |

### 2.2 Conforming packet

A packet conforms to this specification when it declares a profile defined here, carries every resource that profile requires, satisfies every structural requirement of Part 02, and produces no error-level finding from the checks of Part 05.

A conforming packet MAY omit any resource this specification does not require. A validator MUST NOT reject a packet for carrying a resource this specification does not define.

### 2.3 Conforming reader

A conforming reader resolves a packet's resources through its catalog rather than through file layout, checks a resource's declared codecs before opening it, and fails naming what it lacks rather than silently returning partial data (R15 §2).

A reader MUST NOT require an extension schema in order to read core resources (Part 09).

### 2.4 Extension

An extension is a registry document in the format of Part 02, in its own namespace (R17 §2). Core resources never reference an extension's. A validator MUST NOT require an extension's schema in order to validate core, and MUST NOT fail an import because optional extension metadata is absent.

## 3. Normative language

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL are to be interpreted as described in RFC 2119.

Requirements are stated in clauses numbered within each part. A citation of the form `03 §4.2` refers to clause 4.2 of Part 03. A citation of the form `(R53 §2)` refers to a revision document and is provenance, not a requirement.

## 5. Version identifiers

### 5.1 Identifiers a packet records

This document set is v0.2. The identifiers a packet records are unchanged by it, and a packet written against v0.1 remains conforming:

| field | value |
|---|---|
| `profile_id` | `nwb-lake-portable-v0.1` |
| `semantic_standard_version` | `nwb-lake-semantic-v0.1` |
| `logical_standard_version` | `nwb-lake-logical-v0.1` |
| `registry_version` | `0.1.0` |

### 5.2 Recording the registry version

A packet MUST record the registry version it was written against, and SHOULD embed that registry so the packet is self-describing (R2 §8). A packet whose embedded registry disagrees with its recorded version is invalid.

`registry_version` states **compatibility**, and follows semantic versioning: a removed, renamed or retyped column is a major change; an added nullable column is a minor one; a corrected description is a patch.

It is **deliberately held at `0.1.0` while the schema iterates**, so amendments that would otherwise have incremented it — several of them major — have not. A consumer MUST therefore treat the embedded registry as authoritative and MUST NOT use `registry_version` alone to decide compatibility until the hold is lifted. Lifting it is a decision about the schema's stability, not a defect to be fixed.

# Part 00 — Architecture

Normative.

## 1. Scope

This part defines the architecture of an NWB-Lake packet: the vocabulary levels, the layers a packet is divided into, and the storage stance. It defines no schema and no file format; those are Parts 02 and 03.

The design objectives are that a packet be fast to query, straightforward to produce from existing acquisition and sorting outputs, readable from more than one language, independent of HDMF as a runtime data model, and precise enough to drive validation.

## 2. Terms and definitions

### 2.1 Semantic standard

The **semantic standard** defines what concepts mean. A Trial is a bounded interval of experimental time; a Unit is a sorted or curated spiking entity; an ElectricalSeries is sampled extracellular voltage over time and channels.

The semantic standard is independent of storage format, and independent of whether a concept is represented as a table or an array. It is specified in Part 01.

### 2.2 Logical standard

The **logical standard** defines how semantic concepts are represented as computable resources: tables, dense array assets, media assets, document assets, views, materialized tables, materialized arrays, and references between them.

The logical standard is storage-agnostic but not shape-agnostic: trials are logically table-shaped. It is specified in Part 02.

### 2.3 Physical profile

A **physical profile** defines how logical resources are stored. Two are contemplated:

| profile | tables | arrays | catalog |
|---|---|---|---|
| portable | Parquet | Zarr | JSON manifest |
| lakehouse | Iceberg over Parquet | Zarr | JSON manifest plus Iceberg catalog references |

Only the portable profile, `nwb-lake-portable-v0.1`, is specified. It is Part 03.

### 2.4 Packet

A **packet** is one concrete dataset bundle under a declared profile. It may be a local directory, an object-store prefix, or a manifest pointing at distributed assets.

A packet contains a packet catalog, core tables, and any of: dense arrays, media, documents and sidecars, analysis materializations, and validation and provenance records.

A packet is primarily single-session. Multi-session packets are a permitted extension, and a packet declares its sessions in the catalog (R1 §2).

### 2.5 Packet catalog

The **packet catalog** is the dataset-level map. In the portable profile it is `nwb.packet.json`, specified in Part 04.

It records what resources exist, where they live, what semantic type each represents, what logical schema and physical profile each uses, which are canonical and which derived, and what validation and provenance records apply.

### 2.6 Iceberg catalog

An **Iceberg catalog** is distinct from the packet catalog. It is relevant only to the lakehouse profile and manages only tabular resources. It does not catalog dense arrays, media, documents, or semantic relationships across a packet, and therefore does not replace the packet catalog.

### 2.7 Resource identity

Resources and rows reference each other by stable identifier. An implementation MUST NOT use HDF5 object references, Zarr hierarchy paths, host object identity, or file layout as the primary identity system.

## 3. Layer model

A packet is divided into layers by namespace prefix.

| layer | contents | required |
|---|---|---|
| `core` | canonical normalized facts, domain-general | yes |
| extensions | canonical facts a domain owns, typed (Part 09) | no |
| `analysis` | derived products, reproducible from the canonical resources | no |
| `nwb` | deferred compatibility projection | no |

A layer MAY reference a layer beneath it and MUST NOT reference one above (R20 §5.1). Core does not reference analysis, and neither references an extension — a discriminator names without referencing, which is why core is allowed that one (R55 §2.6).

A packet's **canonical** resources are its canonical core resources together with its canonical
extension resources (R71 §2.1). Core is not the whole of what is canonical: R54 sends a task's own
facts — which side the animal licked, whether it was rewarded — to a typed extension, and no
computation over core recovers them. Core is what every packet has and what every consumer can
read without an extension registry.

A consumer MAY read core alone, and what it reads is complete for every core resource. It MUST NOT
conclude it has read every canonical fact the packet holds (R71 §2.4); a discriminator resolving
`required` is the case where the omission is guaranteed.

Extension namespaces are additional to these and are specified in Part 09.

## 4. Core layer

### 4.1 Requirements

The core layer MUST contain canonical facts in the logical schemas of Part 02. Core resources MUST be validated before they are committed.

A fact belongs in core when common interpretation, validation, joining or analysis would break
without it (Part 09 §3). A fact a single domain owns belongs in that domain's extension, typed,
with its own vocabularies and rules — not in core, and not in a free-form column.

Core resources are normalized enough to avoid drift and no further. One row per trial in `core.intervals`; one row per unit in a sorting and curation context in `core.units`; one row per spike in `core.spike_events`.

### 4.2 Spike representation

`core.spike_events`, one row per spike with primitive columns only, is the sole canonical spike representation (R5 §2). The ragged chunked representation of v0.1 is withdrawn, as is the catalog's `canonical_representations` block.

`core.units` carries `n_spikes`, `first_spike_tick` and `last_spike_tick` as a denormalization that a validator checks against `core.spike_events` (R5 §4).

### 4.3 Unit identity

A unit's identity is the tuple `(session_id, unit_id, sorting_run_id, curation_id)`, never `unit_id` alone. A packet carrying sorted units MUST carry `core.sorting_runs` and `core.curation_versions`.

## 5. Analysis layer

### 5.1 Requirements

The analysis layer MAY contain denormalized, prejoined, binned, aligned, or otherwise transformed products. An analysis resource MUST declare lineage to the core resources it derives from.

Analysis resources are disposable. A consumer MAY delete and recompute any of them. An analysis resource becomes canonical only through an explicit revision of this specification.

### 5.2 Materialization is justified by layout, not by arithmetic

A derived product is materialized only where a query cannot answer the same question at acceptable cost. Measurement rather than expectation decides this, and four of v0.1's five proposed analysis resources are withdrawn on that basis (R43 §2).

`analysis.spike_events` is retained: it is core's spikes on the reference clock, bucketed by time and sorted by unit within each bucket, so that a time filter and a unit filter both prune (R30 §2).

## 6. Deferred NWB projection

A packet SHOULD preserve enough semantic metadata to support an NWB-like projection later. This specification does not require PyNWB-compatible object reconstruction, NWB/HDF5 or NWB-Zarr export, or a complete mapping onto the `NWBFile` hierarchy.

Reserved NWB names are not honoured. A projection is therefore a mapping exercise and not a renaming.

## 7. Storage stance

### 7.1 Portable profile first

The portable profile is a JSON manifest, Parquet tables, Zarr arrays, ordinary media files, and text sidecars. It MUST be readable without a server.

### 7.2 Referencing

A packet need not own every byte it describes. Referencing is expected for large resources: a resource the packet does not own sets `external: true` with an absolute URI and declares its own codecs (R14 §2.3, R15 §2).

Externalizing a table costs more than externalizing an array, because a table's validation rules cannot run at all while it is unreachable.

### 7.3 Iceberg later

Iceberg is a later table-management profile, useful for table snapshots, schema and partition evolution, concurrent writers, catalog integration, and reproducible release tags. It MUST NOT be required by an implementation of this specification.

`packet_version` versions the bundle; an Iceberg snapshot would version a table's rows. A rewrite of rows MUST NOT increment `packet_version` (R61 §4).

## 8. Implementation thesis

The first implementation is not a generic NWB backend. It is:

1. a specification of core logical resources;
2. a validator generated from that specification;
3. an importer that turns source data into validated resources;
4. a packet catalog recording the committed resources;
5. a small access library querying tables and arrays with standard engines.

An import succeeds only when validation succeeds (Part 05 §1).

# Part 01 — Semantic Standard

Normative.

## 1. Scope

This part defines what the concepts in a packet mean. It does not decide how they are stored.

Every semantic concept MUST be representable in the logical standard (Part 02). The semantic standard itself is independent of Parquet, Zarr, Iceberg, or any other substrate.

## 2. Global semantic rules

### 2.1 Stable identity

Any object referenced by another object MUST have a stable identifier.

An identifier is a signed 32-bit integer (R53 §2.1). Implementations MUST NOT encode semantic meaning in identifier values, and MUST NOT derive an identifier from a value's position in a file.

Each identifier declares its **identity** (R53 §2.3):

| identity | definition |
|---|---|
| `carried` | the source's own number, reproduced unchanged |
| `assigned` | chosen by the writer when the packet was built |

An assigned identifier's owning table MUST carry a `*_name` column holding the name it was assigned from, so that a process outside the packet can reference the row without knowing the number.

### 2.2 Time basis

Every event, interval, spike time, dense time axis, and media frame timing record MUST declare a time basis: an integer tick and a `clock_id`.

Floating-point seconds MUST NOT be the canonical representation. Seconds MAY be derived, and are defined from the session's time origin (R39 §2.1). A consumer lacking that origin MUST refuse to derive seconds rather than assume one.

A writer that cannot map one of its clocks' observation starts onto the reference MUST NOT declare a time origin (R39 §2.4). An origin it could not compute shifts every second a consumer derives.

A tick is a coordinate, not a label and not a quantity (R45 §3). A writer MUST NOT re-base a source's sample index: for a sample clock, tick 0 is sample 0.

### 2.3 Observation

A session's extent is stated as **wall-clock time**, not as a tick range (R25 §4). A hull over every clock's ticks would need those ticks converted to one clock, and alignment may be anchor-based — outside the first and last anchor the mapping is undefined, which is exactly where a hull reaches. A session therefore declares when it started and MAY declare when it ended, both as instants.

A clock is observing during declared intervals, in that clock's own ticks (R38 §2). Anything timed by a clock inherits that clock's window and MAY refine it, but MUST NOT assert a window derived from its own timestamps.

An interval is **closed**: `start_tick` and `stop_tick` both name observed ticks, so an interval covers `stop - start + 1` ticks and a one-tick interval has `start == stop` (R45 §2).

### 2.4 Provenance

An imported core resource SHOULD be traceable to source data or source activities, and a derived analysis resource MUST declare lineage to the core resources it derives from.

Provenance is a source-file record, a processing-run record, and a link between them (R9 §2). A packet carrying no provenance is conforming; where provenance is present it is validated.

### 2.5 Units of measure

A measured quantity SHOULD declare its unit. A stored integer requiring conversion to physical units MUST declare the conversion.

A unit is declared on the column, not left to the column's name (R56 §2).

### 2.6 Currency

Where several derived results of the same kind and scope coexist, a consumer MUST NOT silently choose between them: it refuses, or reports the ambiguity (R44 §2.2). A preference is declared, keyed on the producing run (R41 §2.3), and a consumer selecting derived data for an activity SHOULD use the preferred run where one is declared for the matching scope (R41 §2.4) — a declared preference a consumer ignores is a preference for nobody.

A run declares the scope it is about (R44 §2.1). A run declaring none is **undeterminable**, which a consumer MUST report separately from ambiguous, and the state is contagious: where more than one run exists for an `activity_type` and **any** of them declares no scope, a consumer MUST NOT conclude the group is unambiguous (R44 §2.3). The unscoped run may or may not be about the same thing as the others, and nothing in the packet says which.

Where a run supersedes another, the chain MUST be well-founded: a run MUST NOT supersede itself, directly or transitively (R41 §2.2).

### 2.7 Extension

Lab-specific concepts MAY be added through namespaced extensions (Part 09). An extension MUST NOT alter the meaning of a core concept without a new semantic version.

## 3. Concepts

### 3.1 Dataset

A collection of packets sharing a semantic and logical standard. It is a organizational concept and has no required representation.

### 3.2 Packet

One concrete bundle of resources under a declared physical profile. A packet MUST declare the sessions it contains.

### 3.3 Session

One continuous recording engagement with one subject.

- MUST have an identifier and a subject.
- MUST declare the clock its times are reported on.
- MUST declare its time origin where seconds are to be derived.

### 3.4 Subject

The animal or preparation recorded from.

- MUST have an identifier.
- SHOULD declare species, sex, and date of birth.

### 3.5 Device

A physical instrument used during acquisition.

- MUST have an identifier.
- SHOULD declare manufacturer, model, and serial number where its source states them.
- SHOULD declare the **hardware revision** and **firmware version** it was running (R66 §2.1).
- SHOULD name the device it was **attached to**, where a source states it (R67 §2.1).

A serial number identifies the object; its firmware determines what the object does. Two sessions can record the same make, model and serial and need interpreting differently, so a version is not an identifier's decoration but a separate fact.

A device is the **physical object**. Where a source presents several recording entities from one object — the bases of a quad-base probe — each is a Probe and all name the same Device; a writer MUST NOT create a second device row for one instrument (R67 §2.2). Attachment is stated, never inferred from a name, and the chain MUST terminate: a device MUST NOT be its own ancestor (R67 §2.3, §2.4).

Both versions are recorded **verbatim** as the source stated them, and MUST NOT be normalised, padded, or parsed into components. Neither is ordered: a consumer MAY compare two version strings for equality and MUST NOT compare them for precedence, because different manufacturers' schemes share none.

Each element of an acquisition chain that reports its own versions is its own device. A value the source gives as unknown is recorded as the source gave it, which is distinct from a source that said nothing.

### 3.6 Probe

A device that carries electrodes.

- MUST belong to a session's device inventory.
- MAY declare manufacturer, part number, and geometry.

### 3.7 Electrode

One recording contact.

- MUST belong to one probe.
- MAY have a position in one or more coordinate frames.

### 3.8 Coordinate

A position of an electrode or unit in a declared frame.

- MUST declare the frame it is in.
- MUST declare the **basis** of its claim (R58 §2.1, R64 §2.1):

| basis | meaning |
|---|---|
| `planned` | where the probe was meant to go; intent, and possibly missed |
| `measured` | where it was, established after the fact by observation |
| `nominal` | where it is by construction; nothing aimed at it and nothing observed it |

The vocabulary is open. A consumer that does not recognise a basis MUST NOT treat the coordinate as `measured` (R58 §2.2).

A coordinate MAY carry an atlas annotation: the structure the position falls in, as an identifier and a label (R59 §2). An electrode is not in a region; a position is, so the annotation belongs to the coordinate rather than to the contact.

Where the identifier is present the label SHOULD be too, so a consumer without the atlas can still read the annotation. A structure's full name and its ancestry path MUST NOT be carried as columns: both are derivable from the identifier, and an ancestry path is a list, which Part 02 §5.2 forbids in a delimited string.

A validator MUST NOT treat an absent annotation as a finding. A position outside any declared structure, or one no registration covered, is a fact about the session.

A coordinate SHOULD name the processing run that produced it where the writer knows it (R60 §2). That is provenance — which run produced the row that is there — and not a choice between rows.

### 3.9 Clock

A monotonic counter with a declared rate and origin.

- MUST declare a tick rate, as a rational where the rate is not an integer (R4 §4).
- MAY declare a parent clock, and if so MUST be alignable to it.
- MUST declare either a linear transform or anchor points, never both (R13 §2).
- MAY bind its **tick 0 to a wall-clock instant** (R6 §2), which is the only route from a
  packet's ticks to real time; absent it, ticks relate to each other and to nothing else.
- A counter that resets mid-session is two clocks (R27 §6), one per epoch, each with its own
  identifier, origin and wall-clock binding. A packet MUST NOT represent a reset as a
  discontinuity within one clock: an anchor sequence requires both sides to increase, so there
  is no way to express it and no way to read it.

A clock's tick-zero binding and a session's start time are **independent and MUST NOT be
conflated** (R6 §4). One is a property of a counter, the other a fact about when work began.
Where a wall-clock binding is derived rather than declared, the tick it is anchored on MUST lie
in the same epoch as the instant it is paired with (R27 §6.2) — a binding computed across a reset
describes neither clock.

An importer MUST examine a source in acquisition order and MUST NOT assume monotonicity (R27
§6.1). A reset is visible only in the order the samples arrived; sorting first hides it.

A tick's zero is where the clock's declared origin says it is — for a sample clock whose origin is
sample 0 of a recording, tick 0 **is** that sample. A writer MUST NOT re-base a source's sample
index and a reader MUST NOT assume any base beyond what the origin declares (R45 §3); that
prohibition is what makes a tick exact.

Alignment beyond the terminal anchors is defined only while the estimator's error stays within tolerance, 3 ms at p95 by default (R37 §3, R40 §2). A profile or a recipe MAY state a different tolerance; a writer MUST record the value it used.

A writer reaching past one median anchor interval MUST measure its error and MUST record the median, p95, and maximum, so a consumer can judge the packet by a stricter rule than the writer applied.

A consumer MUST **report** ticks it cannot map rather than omitting them (R27 §5.3), so a converted table has the same row count as its source with nulls where the mapping is undefined. A row that vanishes in conversion is indistinguishable from one that was never there. It MUST record how many rows it dropped for falling outside the bound **even when that count is zero** (R40 §2.3): silence is what lets a reader and a writer disagree about which rows exist.

### 3.10 Interval

A bounded span of experimental time within a session (R54 §2.1).

- MUST belong to one session.
- MUST have start and stop ticks on a declared clock, closed per §2.3.
- MUST declare its **kind**: the resource that specialises it.

A trial is one kind of interval. Blocks, epochs, and stimulation periods are others. What an interval *means* — condition, stimulus, choice, outcome, stimulation parameters — is declared by the specialising resource and MUST NOT be added to the core interval (R54 §2.3, §2.4).

### 3.11 Event

An instantaneous or near-instantaneous timestamped observation.

- MUST belong to one session.
- MUST have an event type and a tick on a declared clock.
- MUST belong to an event stream.
- MAY carry a structured payload.

An event does not reference an interval (R11 §5). Examples: stimulus onset, reward delivery, lick, threshold crossing, TTL edge, synchronization pulse.

### 3.12 Event stream

The context an event was observed in: what produced it, and on what clock (R23 §2).

### 3.13 Unit

A sorted or curated spiking entity.

- MUST be identified by session, unit, sorting run, and curation version together.
- MUST belong to one sorting run and one curation version.
- MAY sit on several electrodes, and MAY have a position in one or more frames.

A unit is not a neuron. It is what a sorting produced.

### 3.13.1 A rate needs a denominator

A firing rate is a count over a duration, so the duration MUST be knowable. Where a unit declares observation intervals, the rate is its spike count over the total of those intervals; where it declares none, it is the count over the recording's extent (R18 §4). A packet SHOULD state which denominator it used, because the two differ for any unit that drifted out and back.

### 3.14 Spike event

One detected action potential of one unit, at one tick on one clock. Spike events are the canonical spiking representation (R5 §2).

### 3.15 Quality label

An assessment of a unit by one scorer. A unit has many, not one (R16 §2).

- MUST name the source that assigned it.
- MAY carry the source's own label verbatim, which is open.
- MAY carry a normalized label from a closed vocabulary (R22 §2).

### 3.16 ElectricalSeries

Sampled extracellular voltage over time and channels, represented as a dense array asset with a declared time axis and channel mapping.

### 3.17 Array asset

A dense array stored outside the table layer, with declared axes. An axis declares its coordinates; a regularly sampled axis declares them as an origin, a step, and a length rather than as stored values (R20 §2.1).

An array asset holds **any** sampled quantity, whatever instrument produced it. This standard names the concepts it defines — §3.16 is the one it defines for extracellular voltage — and it does not enumerate instruments. A packet names its own arrays, and an array names the device that made it (§3.5); a rig fitted with an instrument this standard has never heard of therefore needs no extension, no new concept, and no revision.

`semantic_type` is open (R8 §4). A value this standard does not define is a label and carries no contract, which is the honest state of affairs for a quantity whose meaning lives in the device rather than in the format.

An array asset SHOULD name the device that produced it, where the writer knows which one did (R65 §2.1). A consumer MAY then resolve any array to its instrument without knowing what kind of array it is, and MUST NOT infer an instrument from an asset's `semantic_type`, its name, or its URI: those are labels, and the device is a reference.

### 3.18 Media asset

An image or video stored in an ordinary container, with frame timing carried in tables.

- MUST have a stable media asset ID, a URI, and a format.
- SHOULD carry a frame table where synchronization matters.

A frame row is indexed by **presentation order**: row *n* describes the frame the asset presents nth, counting from 0 (R69 §2.1). A writer MUST NOT number frames in the order the container stores them, which differs wherever a codec reorders — a stream with bidirectional frames displaces one by several positions, and the resulting misattribution of time is monotonic and therefore invisible.

The index counts the frames the asset **holds**, not the exposures the capture produced. A frame lost before or during writing gets no row and no reserved index (R69 §2.2); what went missing is recorded in the columns that carry timing, not as a gap in the numbering.

A frame's time is a tick on a declared clock, like every other time in a packet (§2.1). A container's own **presentation timestamp** is a different quantity and is carried separately: an integer in the container's own time base, verbatim (R68 §2.1, §2.2). A writer MUST NOT rescale it to seconds, to a clock's ticks, or to a frame number, and MUST leave it absent where it did not read the container. It is not a time on any clock the packet declares, so a consumer MUST NOT compare it between assets or use it to measure elapsed time (R68 §2.5); what it locates is the frame inside the file.

The asset declares the **rate** those timestamps count at, as an exact rational (R70 §2.1) — a container time base of 1/16000 s is 16000 over 1, in the shape a clock's tick rate already uses. A writer that carries presentation timestamps MUST declare it and MUST NOT declare half of it. A consumer MAY then convert a timestamp to seconds of the asset's own timeline without opening the media, which is the case a referenced asset makes ordinary: the file is the part a packet is least likely to have.

### 3.19 Source file

An input the packet was built from.

### 3.20 Processing run

An activity that produced resources, declaring what it was, what it ran on, and the scope it was about.

### 3.21 Sorting run

A processing run that produced units from a recording, declaring the clock its ticks are on (R38 §3).

### 3.22 Curation version

A named state of a sorting's unit set, optionally derived from a parent curation.

# Part 02 — Core Logical Schemas

Normative.

## 1. Scope

This part defines how a logical schema is declared, what a declaration must contain, and which resources the core layer comprises.

The column-level definitions themselves are not written here. They are data (§9), carried in a registry document that a packet embeds and that generates the checks of Part 05. This part is the rules the registry obeys; the registry is the schema.

Two renderings of that registry accompany this specification and are **generated, never edited**: `registry/logical_schemas.json`, which is normative and is what a packet embeds, and `registry/tables.md`, a human-readable listing of every table and column with the revision that introduced each (§9.4). Where this part and a rendering disagree, this part states the rule and the rendering states the current content.

## 2. Table resource requirements

Every table resource MUST declare:

- a schema identifier;
- an ordered list of columns, each conforming to §3;
- a primary key, or `null` with a stated reason (R7 §2);
- its references to other tables (§7);
- its Tier 2 validation rules, if any (§10.2).

## 3. Column declaration

Every column MUST declare a name, a type, a presence, and a role. It MAY declare an identity, a vocabulary, a unit, a clock, and the revision that introduced it.

| attribute | required | clause |
|---|---|---|
| `name` | yes | §4 |
| `type` | yes | §5 |
| `presence` | yes | §6 |
| `role` | yes | §8.1 |
| `identity` | for identifiers | §8.2 |
| `enum` | for closed vocabularies | §9.3 |
| `resolves`, `discriminates` | for discriminators | §8.3 |
| `unit`, `unit_from`, `clock_from` | where applicable | §8.4 |
| `since` | recommended | §9.4 |

## 4. Naming

Column names MUST be lowercase snake case.

| suffix | use |
|---|---|
| `_id` | a stable identifier |
| `_name` | the name an assigned identifier was assigned from |
| `_tick` | a tick coordinate on a declared clock |
| `_uri`, or bare `uri` | a URI |
| `_index` | a zero-based offset into a sequence |

A name is a property of the registry rather than of any packet's rows, so naming is checked against the declaration and not by a validation rule (R48 §4). An exception MUST be declared with a reason.

A source-provenance label — `local_electrode_label`, `local_channel_label`, `local_unit_label` — is a `string` carrying whatever base the producing software used, and MUST NOT be used as an offset into any packet resource (R5 §5, R8 §2).

## 5. Type system

### 5.1 Permitted types

A column's type MUST be one of:

```text
string  int32  int64  float32  float64  bool  timestamp  date  json_string
```

### 5.2 No nested types

`list`, `struct`, and `map` MUST NOT be used (R3 §2.1). A repeated value becomes a child table; a semi-structured value becomes a `json_string` in an optional column.

This keeps a conforming reader able to satisfy every required column without a JSON parser, and keeps a native reader viable in a language without an embedded SQL engine.

A writer SHOULD NOT fill a `json_string` column routinely. Doing so defeats that guarantee in practice: a column present on every row forces a parse on every row, in exactly the table where a consumer works. A value that varies per row and is queried belongs in a typed column of a specialising resource; a value constant across the table belongs once, on the table that owns the whole.

### 5.3 Fixed representations

A writer MUST NOT use wraparound, truncating or saturating semantics for a value whose role is `identifier`, `coordinate`, `structural_index` or `sequence_position`, nor for arithmetic over interval bounds. A conversion whose result would fall outside the declared type MUST fail before the value is written, naming the column and the value (R76 §2.1). A validator is not required to re-derive this: a wrapped value is a valid value of its type and the evidence is gone by the time rules run.

Tick columns MUST be `int64`. Wall-clock columns MUST be `timestamp` with microsecond precision in UTC, and MUST NOT use INT96. Identifier columns MUST be `int32` (R53 §2.1), except where the number of distinct values may exceed `int32`, where the column MUST be `int64` (R53 §2.4). No core table is near that bound; an extension declaring an identifier over more than 2^31 rows declares `int64` for it.

## 6. Presence

A column is `required`, `nullable` or `optional` (R2 §5):

| state | the column | its values |
|---|---|---|
| `required` | MUST be present | MUST be non-null in every row |
| `nullable` | MUST be present | MAY be null |
| `optional` | MAY be absent | MAY be null where present |

The third state is what R3 §2.1 confines a `json_string` to: a conforming reader must be able to
satisfy every required column without a JSON parser, so a column holding JSON is never required.

A present nullable column is preferred to an absent one, because a stable column set simplifies query code. A schema MUST NOT declare a column that duplicates what the data already declares: `core.array_assets` carries no dtype or shape, because the array declares them (R3 §3.0).

Duplication is permitted only where it buys otherwise-unavailable access. Axis names are carried in `core.array_dimensions` because a Zarr binding in another language cannot see them.

## 7. References

A table declares each foreign key as a reference naming the target resource, this table's columns, and the target's columns. A reference MAY be composite, nullable, or self-referencing (R46 §2).

A reference MUST relate columns of the same role, and of the same identity where both are identifiers. Relating an assigned identifier to a carried one resolves to nothing.

## 8. Column semantics

### 8.1 Role

Every column MUST declare exactly one role, from a closed vocabulary with no default (R48 §2.1, R55 §2.1):

| role | meaning |
|---|---|
| `data` | a value to be read |
| `identifier` | a stable identity, per §8.2 |
| `coordinate` | a position on an axis, such as a tick |
| `structural_index` | a zero-based offset into a stored sequence |
| `sequence_position` | an ordinal within an ordered set |
| `discriminator` | a value naming the resource another column resolves against |

The role is what makes index-base conversion derivable from a packet rather than hard-coded in each one-based client (R3 §6). A `structural_index` converts at the client boundary; a `coordinate` does not.

### 8.1.1 Index base

A **structural index** addresses a position in a stored resource and MUST be a **0-based offset**. A client converting to a 1-based language MUST convert at the boundary (R3 §6); the format picks one base and clients adapt, because an offset whose base changes per reader is not an offset.

A **source label** is copied verbatim from acquisition or sorting software. Its base is whatever that software used, and it MUST NOT be used as an offset into any packet resource.

A **coordinate** is neither: copied verbatim like a source label, but used arithmetically, which a source label MUST NOT be (R45 §2.5). Its zero is where its clock's origin says it is.

Because a reference relates columns of the same role (§7), converting every structural index at a boundary is join-preserving by construction.

### 8.2 Identity

An `identifier` column MUST declare `carried` or `assigned` (R53 §2.3). A table owning an assigned identifier MUST carry the corresponding `*_name` column.

A `carried` identifier gets no name column and MUST NOT be given one: the value is already the source's own, so a name beside it would be a second identity for one thing.

### 8.3 Discriminator

A `discriminator` column MUST hold a dotted resource identifier, and MUST declare `resolves` as `required` or `optional` (R55 §2.2):

| `resolves` | an unresolvable value is |
|---|---|
| `required` | a defect: the row is uninterpretable |
| `optional` | a fact: the packet does not hold that resource |

A reader SHOULD offer the resolution: read the kind, take that resource's key from the registry,
join (R55 §2.3). A discriminator nothing reads is a free-form name with extra steps, which is the
observed fate of the mechanism this one replaces.

Where a discriminator is paired with a value column, both are nullable and the two MUST agree — a
row declares both or neither (R49 §2.4). A row declaring neither is **undeterminable**, which a
consumer MUST report apart from a row whose value resolves to nothing: the fix for one is to record
the missing half, and for the other to correct what it names.

Resolution takes one of two shapes, and a discriminator declares which by whether it names a paired column.

**Shared key.** The discriminated row and the named resource share a key, so the join is on that key. A resource a shared-key discriminator may name MUST declare a reference back to the discriminated table, and that reference MUST cover the discriminated table's **whole key**. A reference on part of it targets a set that is not unique — it identifies a row of some kind, which is not a foreign key, and the generated anti-join passes while resolving to several rows.

The checks a discriminator implies MUST be generated over **every resource the packet declares, extensions included** (R55 §2.5). Building them over core alone is the defect R55 was written for: an extension kind matched no branch and passed in silence, which is the one case the mechanism exists to cover.

A detail table therefore carries the discriminator as a constant column, restating in every row what its own identity implies. A column holding one value costs almost nothing once encoded, and what it buys is a reference that identifies a row.

The reference runs extension → core, so a discriminator names downward while the integrity constraint points upward.

**Paired value.** A separate column holds an identifier in the named resource's key space, and the discriminator MUST declare `discriminates` naming that column. A paired value holds one identifier, so the named resource's primary key MUST be a single column, and the value MUST be a `string` matching that key where it is `carried` or its `*_name` where it is `assigned`.

Core MAY name an extension's resource through a discriminator. It MUST NOT reference one (R55 §5): naming does not create a dependency.

### 8.4 Unit and clock

A `data` column carrying a physical quantity SHOULD declare its `unit`, or `unit_from` naming a column that carries it (R77 §2.2). A `coordinate` column MUST declare `clock_from` where the clock its ticks are on is not the one that row's `clock_id` names, and MUST declare it where the table has no `clock_id` at all (R77 §2.1). Measured across the registry, 6 of 20 coordinates declare one and the other 14 resolve to their own row's clock; none has neither.

`clock_from` names a column of the same table or a one-hop `resource.column`. A consumer resolves it rather than guessing, because converting on the wrong clock fails silently.

A consumer MAY label a quantity with its declared unit, and MUST NOT silently compare or combine two columns whose declared units differ (R56 §2.5).

## 9. The registry

### 9.1 The schema is one document

Table structure and validation rules are carried in one JSON document (R2 §2). It declares the semantic and logical standard versions, its own registry version, and its tables.

### 9.2 Self-description

A packet MUST record the registry version it was written against and SHOULD embed the registry itself, so the packet stays readable as the reference registry moves on (R2 §8). A packet whose embedded registry disagrees with its recorded version is invalid.

A registry document SHOULD carry a top-level `$schema` naming its meta-schema (R57 §2.1). A
validator MUST NOT dereference it and MUST NOT require it.

Where `$schema` is present it MUST equal the `$id` of a meta-schema the consumer holds, or the
document MUST be reported as governed by a schema this consumer does not have — an **`info`**
finding, not an error (R57 §2.2). R17 §4 already says a core validator is not required to hold an
extension's schema, and the same reasoning applies one level up.

### 9.3 Vocabularies

A vocabulary is open unless the column declares `enum`. A validator MUST reject a value outside a declared `enum`, and MUST NOT reject an unrecognized value from an open one (R8 §4).

Three columns are closed:

| column | values |
|---|---|
| `core.processing_runs.status` | `succeeded`, `failed`, `partial` |
| `core.units.quality_label` | `sua`, `mua`, `noise` |
| `core.unit_quality_labels.normalized_label` | `sua`, `mua`, `noise` |

A scorer's own `label` is open, because aggregating over scorers is incompatible with one closed set (R22 §1).

### 9.4 Provenance of a declaration

A table and a column SHOULD each carry `since`, naming the revision that introduced or last changed it (R77 §2.3). The registry stamps both: 15 tables and 172 columns carry one.

A column whose role is declared SHOULD NOT restate its base in its description (R48 §2.5). The role carries it, and prose repeating it is a second statement that can disagree with the first.

## 10. Validation rules

### 10.1 Tier 1: generated from structure

A validator MUST generate, from the declaration alone: required-column non-null checks, primary-key uniqueness, foreign-key anti-joins, and closed-vocabulary membership. A nullable foreign key is guarded with a null test.

Uniqueness need not be checked by query where a table's physical sort begins with its primary key, since duplicates are then adjacent and the ordering scan settles it.

### 10.2 Tier 2: declared

A rule the structure cannot imply is declared as SQL returning offending rows, or as a named template the registry build expands (R24 §2).

The execution contract is the whole protocol: **a check's query returns offending rows; empty is a pass, non-empty is a failure, and the returned rows are the finding.**

A rule declares a level of `error`, `warning`, or `info`. A rule MAY be `advisory`, in which case
it is off by default and MUST NOT be `error`, so that enabling it cannot change whether a packet
previously passed. Stated as the guarantee it is: **running with advisory rules enabled MUST NOT
change whether a packet passed** (R26 §4). A validator MUST expose the choice, and a report MUST state whether
advisory rules were run: two reports over one packet may legitimately differ, and one that does
not say which mode produced it cannot be compared with the other.

### 10.3 What is not a rule

Physical order, file presence, Parquet types, Zarr rank and codecs, and checksums MUST NOT be expressed as SQL (R12 §4). A query cannot observe them, so a storage-layer check written as SQL fails silently rather than loudly. These are checked by the shim of Part 05 §5.3.

# Part 03 — Portable Physical Profile

Normative. Profile identifier: `nwb-lake-portable-v0.1`.

## 1. Scope

This part defines how the logical resources of Part 02 are stored in the portable profile. A packet under this profile MUST be readable without a server.

## 2. Required technologies

| resource kind | format |
|---|---|
| catalog | JSON |
| tables | Apache Parquet |
| dense arrays | Zarr, v3 for packet-owned arrays (§6.1) |
| media | ordinary containers, such as MP4 |
| documents | Markdown, JSON, text, or PDF |

## 3. Directory layout

### 3.1 Recommended layout

```text
packet_root/
  nwb.packet.json

  tables/
    core/           <resource>.parquet
    analysis/       <resource>.parquet
    <namespace>/    <resource>.parquet      extension tables

  arrays/
    core/           <array_asset_id>.zarr/
    analysis/       <array_asset_id>.zarr/

  media/            <media_asset_id>.<ext>

  extensions/       <name>.json             extension registries

  schemas/
    logical_schemas.json                    the embedded registry

  manifests/        <packet_version>.json   superseded manifests

  docs/                                     human-readable sidecars

  validation/       validation_report.json
```

The catalog MUST record the actual layout. A reader MUST resolve resources through the catalog and MUST NOT infer them from paths.

### 3.2 Files that MUST NOT be written

`schemas/semantic_version.txt` is struck (R62 §2). It restated `semantic_standard_version`, which the catalog is required to carry, and so bought no otherwise-available access.

## 4. URI rules

A URI in the catalog or in a table MAY be relative to the packet root or absolute. A portable local packet SHOULD use relative URIs.

An absolute URI MAY name an external asset. An external asset MUST be declared as such in the catalog (Part 04 §5).

## 5. Table storage

### 5.1 Encoding

A table MUST be a valid Parquet file. Compression SHOULD be Zstandard where available.

A large table SHOULD use row groups sized for analytical scans; 100,000 to 1,000,000 rows is a starting point to be adjusted by profiling.

An identifier column is `int32`, or `int64` where its range requires it (Part 02 §5.3) and MUST NOT be dictionary-encoded in a way that requires unification across row groups before it can be compared.

### 5.2 Partitioning

A large multi-session table SHOULD be partitioned by `session_id`. A table MUST NOT be partitioned by `unit_id`, which produces many small files.

A partitioned table's row order across files is not defined by this profile. A single file is therefore preferred where the table's sort is load-bearing.

### 5.3 Ordering

A writer SHOULD sort every table by its primary key, in the order the key declares, unless a different ordering is specified for that table (R10 §2). A table written in another order is still conforming: row order is a physical property, it carries no meaning, and a reader MUST NOT depend on it for correctness.

What it is for is pruning. A validator establishes it by scan rather than by query, because physical order is not visible to SQL (R12 §4, Part 02 §10.3), and reports a departure at **warning** level — a packet whose rows are out of order is readable and slower, not wrong.

Two tables override the default, both specified below, and `analysis.spike_events` overrides it under a `MUST` (R30 §3.2).

### 5.4 The overriding orders

| resource | order |
|---|---|
| `core.spike_events` | `session_id, sorting_run_id, curation_id, unit_id, t_tick` |
| `core.events` | `session_id, clock_id, t_tick` |
| `analysis.spike_events` | `session_id, clock_id, time_bucket_tick, sorting_run_id, curation_id, unit_id, t_tick` |

A writer **MUST** emit `analysis.spike_events` in that order (R30 §3.2). It is the one resource whose layout is part of its reason for existing: bucketing by time and sorting by unit within each bucket leaves both columns with informative row-group statistics, so a unit filter and a time filter each prune.

A writer **SHOULD** start a new row group at each bucket boundary (R30 §3.3). A group cut at a fixed row count straddles boundaries and spans two buckets' worth of time. Row-group size and encoding are otherwise not normative: the right values follow from session length and unit count rather than from the schema.

### 5.5 The Parquet floor

A reader MUST support the compressions **uncompressed, Snappy, Gzip and Zstd**. A writer MUST use
one of those four and SHOULD use Zstd (R3 §2). Dictionary, RLE and delta encodings MAY be used and
MUST be supported by readers.

A writer SHOULD encode tick columns with `DELTA_BINARY_PACKED` and SHOULD NOT dictionary-encode
them. On a high-cardinality tick column a writer builds a dictionary nearly as large as the column,
abandons it at its size threshold, and emits a mix of partial-dictionary and plain pages larger
than either encoding alone.

Wall-clock timestamps MUST be Parquet `TIMESTAMP` with `isAdjustedToUTC=true` and `MICROS`
precision; `INT96` MUST NOT be used. Dates MUST be Parquet `DATE`, int32 days since the Unix epoch.

## 6. Array storage

### 6.1 Version

A packet-owned array MUST be Zarr v3 (R21 §3.1). A referenced array MAY be Zarr v2, because a packet does not control how an external producer wrote it.

An array MUST use a **regular chunk grid** (R3 §7.1): every chunk the same shape, the last along each axis permitted to be partial. An irregular grid is expressible in Zarr and is not readable by every binding.

Stated as the prohibition a validator can check: `physical_profile: "zarr_v2"` MUST NOT appear on a resource that is not `external: true` (R21 §3.2).

Each array resource declares its own Zarr version in the catalog. A reader MUST check a resource's `physical_profile` together with its `codecs` before opening it, and MUST fail **for that resource**, naming whichever it lacks — the per-resource degradation R15 §2 requires applies to the version as much as to the codec, because a reader may support a codec in one Zarr version and not the other.

### 6.2 Axis order

Array axes are stored order, slowest-varying first (R3 §5). The `transpose` codec MUST NOT be used.

A column-major binding enumerates axes in reverse. The client adapts; the format does not.

### 6.3 Axis coordinates

Every axis MUST declare its coordinates in `core.array_dimensions`, in one of the forms of R20 §2. A regularly sampled axis declares an origin tick, a step, and a length rather than storing per-sample values.

A step MAY be rational, declared as a numerator and denominator (R33 §2): a 30 ms bin at 31,250 Hz is 937.5 ticks.


An axis MUST declare no more than one coordinate form: two descriptions of the same positions can disagree and nothing would say which governs (R20 §3).

A rational step is a numerator and a denominator. `step_tick_den`, where present, MUST be positive, the numerator MUST be present wherever an origin is, and the pair SHOULD be in lowest terms so two packets describing the same axis describe it identically (R33 §2).

Where an array declares both a sampling rate and a regular tick axis, the two describe the same thing and MUST agree (R20 §4). The rate is retained as a validated denormalization, not as a second source of truth.

### 6.4 Codecs

A writer MAY use any Zarr codec. The catalog MUST name every codec a resource uses. A reader MUST check a resource's declared codecs before opening it, and MUST fail naming what it lacks rather than returning partial data (R14 §2.2, R15 §2).

The floor a reader is required to support is stated per Zarr version, because implementations differ between them (R21 §3):

| `physical_profile` | a reader MUST support | a writer MAY also use |
|---|---|---|
| `zarr_v3` | `none`, `gzip`, `zstd` | `blosc` (cname=zstd, shuffle=shuffle), `sharding_indexed` |
| `zarr_v2` | `none`, `zstd`, `blosc` (cname=zstd) | — |

The asymmetry between the versions is measured, not chosen: `gzip` is in the v3 floor and not the v2 one because a v2 array compressed with gzip raises `KeyError: "gzip"` in a reader that reads every other combination. Codecs are declared per resource, not per packet: a reader MUST NOT refuse a packet over a codec used only by resources it does not open. The catalog's packet-level codec list is their union, for a whole-packet capability answer.

### 6.5 What the array declares, and what the tables declare

`core.array_assets` MUST NOT carry dtype or shape. The Zarr array declares them, and restating them buys no otherwise-unavailable access (R3 §3.0).

`core.array_dimensions` carries axis names, because a Zarr binding in another language cannot see them.

Zarr attributes MAY duplicate helpful metadata. Metadata required for validation MUST also be represented in tables or the catalog, so that it is not reachable only through an array store.

## 7. Metadata placement

| kind | location |
|---|---|
| packet-level facts | the catalog |
| queryable scientific facts | tables |
| semi-structured, lab-specific values | a `json_string` column, or a sidecar |
| human-readable context | `docs/` |

A value used for filtering, grouping, joining, or validation MUST be a first-class typed column.

## 8. Immutability

### 8.1 Packet-owned bytes

A resource the packet owns MUST NOT be modified in place once committed (R14 §2.3). A correction is a new packet version, not an edit.

This promise is what allows an amendment to skip revalidating untouched files (R35 §2), so it is verified rather than assumed: a writer records a checksum for every packet-owned resource (§10).

### 8.2 External bytes

This specification promises nothing about bytes the packet does not own. What a packet records about an external resource is what was true when it was checked, not a claim about now (R14 §2.3.1).

## 9. Amendment, versioning, and retention

### 9.1 What an amendment is

An **amendment** produces a new version of an existing packet and MUST NOT modify any file the superseded manifest names (R32 §2). A table that gains rows is written as a **new file**, and the amended manifest names the new file; no byte of the old one changes. Immutability is thereby a property of files, and a resource's *content* may be superseded by naming different bytes.

An amendment MUST set a `packet_version` that sorts strictly after the superseded one, compared as a semantic version.

### 9.2 What an amendment may and may not do

| | |
|---|---|
| Add an analysis resource | MAY |
| Add rows to a provenance table (`core.processing_runs`, `core.source_files`, `core.processing_run_inputs`), as a new file | MAY |
| Remove an analysis resource | MAY — Part 06 makes them disposable |
| Add a core resource | MAY |
| Change the content of a core resource other than the provenance tables | MUST NOT |
| Remove a core resource | MUST NOT |
| Change `packet_id`, `profile_id`, or the standard versions | MUST NOT |

The asymmetry is the design: an amendment **extends** what a packet says and does not revise it. A packet whose core data was wrong is a new packet, not a new version of an old one, because anything already derived from the old core is silently invalidated and nothing in the format can detect that.

Provenance tables are the exception because they are append-only by nature — a row records that something ran, and a later run does not change what an earlier one did.

### 9.3 The manifest

Every superseded manifest is retained under `manifests/` (R32 §4), so a later cleanup can distinguish a file an old version named from a file nothing ever named. A retained manifest keeps its own `created_at` and its own validation record; an amendment MUST NOT rewrite either.

Where an amendment installs a different registry, the packet retains the superseded copy alongside it (R32 §4.1). Installing different content under a `registry_version` the packet has already retained makes that version ambiguous **within one packet**, and a writer MUST refuse it.

### 9.4 Scope of revalidation

An amendment MUST validate the whole packet, not only what it added (R32 §5). What R35 bounds is
the *work*, not the verdict: the resources an amendment did not write are immutable, so their
verdict is determined rather than assumed, and re-establishing it costs nothing.

An amendment MUST establish the physical order of the resources it writes, and MUST NOT be required
to re-establish it for any other packet-owned resource (R35 §4).

A check MUST be re-run when it is **attached to** a resource the amendment writes, **or when its
query names one**; a check meeting neither condition MAY be skipped (R35 §2). The second test is
syntactic — a generated check refers to a resource by its flattened name — so a rule that names a
resource added later is caught without the registry having to declare that it might.

The test **MUST be over-inclusive where it is uncertain** (R35 §5). Matching a resource name inside
a string literal or a comment re-runs a check that did not need it, which costs time; failing to
match one costs correctness. An implementation that cannot show an input is immutable MUST run the
check (R35 §6): skipping a check whose inputs *could* have changed stays forbidden, which is what
R32 §5 was protecting.

### 9.5 Cleanup

Cleanup is a separate operation and MUST proceed orphans first, superseded manifests second (R61 §2.1). Expiring a manifest first would make an orphan indistinguishable from a stray, permanently.

A **stray** — a file no manifest ever named — MUST NOT be removed (R61 §2.1). A packet may carry
files this specification does not govern, and cleanup that deletes the ungoverned is a data-loss
bug wearing an operation's name. The operation reports by default and acts only when asked.

An amendment **MUST NOT** delete anything as part of amending (R32 §6). A file that no manifest
version names any longer MAY be deleted, but by cleanup, as a separate operation — which is what
keeps an amendment's failure from having removed something.

A packet MAY declare its own retention, and a writer SHOULD emit one (R61 §2.2): how many superseded manifests to keep, and an optional age beyond which one may be dropped. Both are **floors** — a manifest is expired only when both permit it — and both default to one kept version and no age limit, because a packet is archival where a table is operational. A packet never amended retains nothing and carries no `manifests/` directory at all, so the common case costs nothing.

### 9.6 What a version is not

`packet_version` versions the bundle. It MUST NOT be incremented for a rewrite of a table's rows under a future lakehouse profile (R61 §4).

## 10. Checksums

A writer records a `sha256` over each packet-owned resource by default (R52 §2). This is the one case where a digest verifies what the packet itself claims, and it is cheap: whole-file, one file per resource.

A digest is whole-file, not per-row-group. Parquet cannot be appended to, so "which pages moved" is not a question the format can be asked, and Parquet's own page CRC32 is a corruption detector that a rewritten file passes.

A packet-owned resource recording no digest is not checked, and a verification report MUST state how many it skipped for that reason (R52 §2.3). A pass that does not say what it skipped reports clean on resources it never looked at.

Verification of external resources is optional and layered (Part 04 §5.3).

# Part 04 — Packet Catalog

Normative.

## 1. Scope

This part defines the packet catalog: the document that binds a packet's resources together. In the portable profile it is `nwb.packet.json` at the packet root.

## 2. Principles

The catalog is the packet's map. A reader MUST resolve resources through it and MUST NOT infer them from file layout.

The catalog binds every resource kind, including tables, dense arrays, media, and sidecar documents. An Iceberg catalog manages only tabular resources and therefore does not replace it.

The catalog identifies by name. `packet_id`, every entry's `resource_id`, the session list, and a resource's `processing_run_id` hold names rather than assigned numbers, because the catalog is read before any table and a number resolves against nothing.

## 3. Required top-level fields

| field | type | requirement |
|---|---|---|
| `packet_id` | string | MUST |
| `packet_version` | string | MUST |
| `profile_id` | string | MUST |
| `semantic_standard_version` | string | MUST |
| `logical_standard_version` | string | MUST |
| `registry_version` | string | MUST |
| `created_at` | timestamp | MUST |
| `sessions` | array of string | MUST (R1 §2) |
| `resources` | array of entry | MUST |
| `validation` | object | MUST |
| `required_codecs` | array of string | MUST (§6.2) |
| `extensions` | object | where extensions are present (§8) |
| `description` | string | MAY |

## 4. Resource entries

### 4.1 Common fields

| field | type | requirement |
|---|---|---|
| `resource_id` | string | MUST, dotted and namespaced |
| `layer` | string | MUST |
| `kind` | string | MUST, per §4.2 |
| `physical_profile` | string | MUST |
| `uri` | string | MUST |
| `canonical` | bool | MUST |
| `validation_state` | string | MUST |
| `sha256` | string | SHOULD for a packet-owned resource (R52 §2.1) |
| `schema_id` | string | MUST for a table |
| `codecs` | array of string | MUST for an array (§6.2) |
| `external` | bool | MUST where true (§5) |
| `derived_from` | array of string | MUST for a derived resource (§7) |
| `processing_run_id` | string | MUST for an analysis resource (R31 §3); SHOULD for any other derived resource |

### 4.2 Kinds

| kind | contents |
|---|---|
| `table` | a Parquet table |
| `dense_array_asset` | a Zarr array |
| `media_asset` | an image or video |
| `document` | a sidecar |

### 4.3 Withdrawn blocks

The `canonical_representations` block is withdrawn: spikes have one canonical representation, so there is nothing to arbitrate (R5 §2).

A top-level provenance block is withdrawn. Provenance is carried in `core.source_files`, `core.processing_runs`, and `core.processing_run_inputs`; the catalog records outputs at resource granularity only (R9 §2).

## 5. External resources

### 5.1 Declaration

A resource the packet does not own MUST set `external: true`. A resource whose `uri` is absolute MUST declare `external: true`; **the converse does not hold** (R14 §2.3), so a packet MAY declare a resource external and still resolve it relatively, which is how a packet published beside its data records that it does not own it.

Referencing is expected for large resources. Externalizing a table costs more than externalizing an array: its validation rules cannot run at all while it is unreachable.

### 5.2 What is recorded

`sha256`, `size_bytes`, and `verified_at` record what was true when the resource was checked. They are not a claim about now.

A writer that cannot reach a URI MUST record nothing rather than copying a value from a local stand-in (R36 §2.4).

### 5.3 Verification levels

Verification of an external resource is layered, and a report MUST state which level it reached.

| level | establishes |
|---|---|
| 1 | the catalog is internally consistent |
| 2 | packet-owned resources match their recorded digests |
| 3a | the external resource exists and lists |
| 3b | its recorded per-member store digests still match (R51 §2) |
| 3c | its bytes read and hash to the recorded `sha256` (R36 §2.2) |

Structural validation MUST NOT reach the network. Levels 3a to 3c run only in a requested mode.

### 5.4 Prefix resources

Where a resource is a prefix rather than a single object — an external store, or a packet-owned Zarr array — `sha256` and `size_bytes` are **defined over its members** (R36 §2.2), not undefined:

- `sha256` is the SHA-256 of the UTF-8 encoding of `[["<key>",<size>,"<sha256>"], ...]`, serialised as compact JSON with `,` and `:` separators, no whitespace and ASCII-escaped keys, one entry per object, `<key>` relative to the resource's `uri` with `/` separators, sorted by `<key>` in byte order.
- `size_bytes` is the sum of the members' sizes.

Sorting the keys is what makes the digest reproducible without knowing the store, since two implementations enumerate an object-store prefix and a local directory in different orders. Carrying each member's own digest is what lets a consumer that fetched three chunks verify those three without the other two hundred.

Such a resource MAY additionally declare a `members` array recording what was seen, each member optionally carrying a `store_digest` (R51 §2.1).

A member array is a record, not a resolution rule: a reader hands the prefix to the array library and does not enumerate it.

Where `members` accompanies R36 §2.2's `sha256`, the listing digested MUST be the declared one, so the enumeration and the digest cannot disagree (R51 §2.1).

A validator asked to verify content **without reading** compares each member's recorded `store_digest` against the value the store reports now — a third level between listing and reading (R51 §2.3). A member whose value differs has changed; a member with no recorded `store_digest`, or whose store reports none, is **not checked**, and the report MUST say how many were skipped.

A store digest answers whether anything changed in place. It does not verify a recorded `sha256` — they are different functions — is absent for multipart uploads, and is unstable across a copy. A verification pass MUST report what it skipped for these reasons, and a store-digest pass **MUST NOT** be reported as a checksum verification (R51 §2.4): it establishes something weaker and store-specific, so it gets its own finding.

## 6. Codecs

### 6.1 Per resource

Every array resource MUST declare the codecs it uses. A reader checks a resource's own declaration before opening it (R15 §2).

### 6.2 Packet union

`required_codecs` is the union of every resource's codecs, present so a reader can answer whether it can open the packet at all. A reader MUST NOT refuse a packet over a codec used only by resources it does not open.

A codec declared for an external resource is a claim rather than an observation, and a validator reports it as `info` rather than silently accepting it.

## 7. Derived resources

A derived resource MUST declare `derived_from`, naming the resources it was computed from.

It SHOULD declare `processing_run_id`, naming a run recorded in `core.processing_runs` (R31 §2). A validator resolves that name against the run table's `*_name` column, since the catalog names and the table numbers (§2).

## 8. Extensions

Where a packet carries extension resources, the catalog MUST declare each extension namespace, its version, and the path to its registry document (R17 §4):

```json
"extensions": {
  "dynamic_foraging": { "version": "0.1.0", "registry": "extensions/dynamic_foraging.json" }
}
```

A validator MUST check that a declared extension registry exists. It MUST NOT require an extension's schema in order to validate core.

## 9. Validation block

| field | requirement |
|---|---|
| `status` | MUST: `passed`, `failed`, or `not_run` |
| `validated_at` | MUST |
| `validator_name` | MUST |
| `validator_version` | MUST |

A packet whose committed manifest records `failed` MUST NOT present its resources as canonical.

# Part 05 — Validation and Import

Normative.

## 1. Core principle

**Validation is importation.** Copying bytes into a packet directory is staging, not import.

A resource is imported when it has been discovered, extracted to staging, normalized to the logical schemas, validated, committed, and recorded in the catalog with its provenance.

A staged resource MUST NOT appear in the catalog as a committed canonical resource. Nothing becomes core data before it has passed the validators that apply to it.

## 2. Pipeline

| stage | action |
|---|---|
| 1 | discover what each source offers |
| 2 | extract candidate resources to staging |
| 3 | normalize to the logical schemas |
| 4 | validate the staged resources |
| 5 | commit |
| 6 | record provenance |
| 7 | materialize analysis resources |

An importer MUST NOT combine parsing, normalization, validation, and writing into one opaque step. A source adapter returns records; it MUST NOT write files.

## 3. The session recipe

### 3.1 Purpose

One source is rarely sufficient: integer sample indices come from a sorter, task structure and registration from an exported file, and session identity from acquisition metadata. The unit of work is therefore a **recipe** naming several sources, not a single input file.

A recipe declares, for one packet:

- each source: its kind, its root, and its options;
- which resources each source supplies;
- the clocks the packet declares, and their parents;
- what to materialize;
- session and subject facts no source carries.

### 3.2 The recipe is the provenance record

A recipe MUST be recorded in the import run's parameters, and its digest MUST be recorded as the run's `code_uri`. A committed packet therefore states what produced it.

### 3.3 Ownership

Each source declares its resources as `owns` or `contributes`.

| declaration | meaning |
|---|---|
| `owns` | this source is solely responsible; records another source emits for the resource are discarded |
| `contributes` | this source adds rows alongside others |

`contributes` exists because some resources genuinely have several suppliers. Without the distinction, the last adapter to run wins silently.

### 3.4 What a source can produce

Every source adapter MUST declare `PRODUCES`, the set of resource identifiers it can supply (R63 §2.1). It is static: a property of the adapter, readable with nothing open, and distinct from what a particular source root happens to hold.

A source entry that declares no `owns` MUST be read as owning every resource in its adapter's `PRODUCES` that no other source owns (R63 §2.2). **A recipe states what it narrows; silence means the whole.**

Where two sources default to the same resource and no preference is declared, the recipe MUST be refused naming both.

### 3.5 Checking a recipe

A recipe MUST be checked against the registry before any source is opened. The check MUST refuse:

- a resource owned by more than one source;
- an owned resource the registry does not define;
- an owned table whose **required** foreign key targets a table nothing supplies;
- a clock declared twice, referenced but absent, or parented to nothing;
- a required source option that is not set.

The check MUST report as a **warning**:

- an owned table whose **nullable** foreign key targets a table nothing supplies;
- a resource some listed source declares in `PRODUCES` that no source claims (R63 §2.3).

A warning is not an error because narrowing is legitimate, and only the recipe's author knows whether this one was meant.

## 4. Stages 1 to 3

### 4.1 Discover

For each source, report what it offers per resource, and how many rows. Discovery MUST NOT write to the packet.

### 4.2 Extract

Copy or stream candidate resources into a staging area under the packet root. A table whose row count is large MUST be streamed rather than materialized as host objects.

### 4.3 Normalize

Map source objects onto the logical schemas: assign identifiers packet-wide before any table is written (R53 §2.5), apply the declared sort, and coerce types to the registry's.

Normalization MUST be deterministic in the recipe. Two runs of the same recipe over the same sources produce the same packet.

An interval is closed (01 §2.3). A source whose intervals are half-open — `[start, stop)` — MUST be converted, which is a subtraction on the stop bound. A writer MUST NOT carry a half-open bound through unchanged.

An adapter compensating for a known defect in its source MUST declare the compensation, and every compensation applied MUST be recorded in the import run's parameters. Choosing not to correct a known defect is equally a compensation and is declared as a pass-through.

## 5. Stage 4: Validate

### 5.1 Tier 1

Generated from structure (Part 02 §10.1): required-column non-null, primary-key uniqueness, foreign-key anti-joins, closed-vocabulary membership.

### 5.2 Tier 2

Declared per table as SQL returning offending rows, or as an expanded template (Part 02 §10.2).

### 5.3 The shim

Physical order, file presence, Parquet types, Zarr rank and codecs, and checksums MUST be checked outside SQL (R12 §4). A query cannot observe them, so such a check written as SQL fails silently rather than loudly.

A claim that crosses from the manifest to a table belongs here for the same reason. A resource's `processing_run_id` lives in the manifest, which no query sees, so the check that it names a run present in `core.processing_runs` is the shim's and not a foreign key (R31 §5).

### 5.4 Extensions

Each extension registry present is validated on the same terms as core, and its verdict is reported separately (R17 §4). A core failure MUST NOT be attributed to an extension, and an extension failure MUST NOT invalidate core.

## 6. Stage 5: Commit

Commit MUST be atomic with respect to a concurrent reader:

1. write the staged resources;
2. validate them;
3. move resources into their final paths;
4. **publish** the packet catalog at `nwb.packet.json`, last and atomically.

A reader MUST observe either the previously committed catalog or the newly published one, and MUST
NOT observe a catalog naming a resource that is not yet in place (R74 §2.1). Every packet-owned
resource the catalog names MUST already be at its final location and MUST have passed validation
before it is published.

The publication mechanism is the profile's. A filesystem profile MAY publish by atomic rename
within one directory; an object-store profile MAY publish by a single-object write. A writer MUST
NOT be required to perform an atomic **directory** rename (R74 §2.2), which no object store
offers and which the packet layout does not need — the catalog is one object.

Where the store offers a conditional write, a writer publishing a new version SHOULD use it, so
two writers cannot silently overwrite one another's head. Where it offers none, a writer MUST NOT
claim it detected a conflict it could not detect (R74 §2.3).

A commit that finds an error MUST NOT write a manifest at the packet root, and SHOULD leave staging in place for inspection.

## 7. Stage 6: Provenance

Record `core.source_files` for the inputs, one `core.processing_runs` row for the import, and `core.processing_run_inputs` linking them. The run declares its `scope` and `scope_kind` (R44 §2, R49 §2).

## 8. Stage 7: Materialize

Materialization runs inside the import: core is staged, the staged packet is opened, derived resources are computed from it, and everything is validated together before anything is promoted.

Deriving into an already-committed packet is an amendment (03 §9.1), not part of an import.

## 9. Reporting

### 9.1 Findings

A finding declares a level, the check that produced it, and a message. Where a check is a query, the offending rows are the finding.

| level | meaning |
|---|---|
| `error` | the packet does not conform |
| `warning` | conformant, but likely not intended |
| `info` | recorded, not judged |

### 9.2 Error policy

An import MUST refuse to commit on any error.

A validator MUST NOT downgrade an error to make a packet pass. An advisory rule MUST NOT be an error (Part 02 §10.2), so enabling advisory checks cannot change whether a packet previously passed.

### 9.3 Comparison against a prior packet

Where an import replaces an existing packet, it SHOULD report every resource the prior catalog declared that the new one does not. This is a warning: narrowing is legitimate, and no other check sees a resource that is simply absent.

## 10. Minimum acceptance criteria

An importer conforms when it:

1. refuses a recipe that cannot produce a valid packet, before opening any source;
2. produces a packet that passes Tier 1, Tier 2, and the shim;
3. records provenance for what it read and what it ran;
4. leaves no manifest at the packet root when it refuses;
5. is **logically deterministic**: for the same recipe, the same source bytes and the same
   declared normalization, it produces the same canonical rows, the same values, the same assigned
   identifiers, the same resource identities and the same declared physical ordering (R75 §2.1).
   Identifier assignment MUST be a function of the recipe and the sources, never of wall-clock
   time, iteration order over an unordered collection, or the order a filesystem listed a
   directory.

Byte-identical output is **not** required and cannot be: a manifest carries `created_at` and
`validated_at`, and encoders may encode identical logical content differently between library
versions. An implementation MAY offer a deterministic-build mode that pins those, and a packet
MUST NOT be judged non-conforming for lacking one (R75 §2.2).

A recorded `sha256` therefore says what a packet's bytes **are**, not what a second build would
produce. Two conforming builds of one dataset may record different digests for the same rows
(R75 §2.3).

# Part 06 — Analysis Layer

Informative, except §2 and §5, which are normative.

## 1. Scope

This part describes the optional `analysis` layer: derived products computed from core, kept because a query cannot answer the same question at acceptable cost.

## 2. Rules

Normative.

An analysis resource MUST declare lineage naming each canonical resource it derives from — core
or extension (04 §7, R71 §2.3).

An analysis resource is disposable. A consumer MAY delete and recompute any of them without loss.

An analysis resource MUST NOT be the only place a fact exists. Anything a consumer needs that is
not recomputable from the canonical resources belongs among them (R71 §2.3); which canonical layer
it belongs to is decided by Part 09 §3's test, not by this rule.

## 3. What justifies materializing

A derived product earns its place by **layout**, not by arithmetic. Where the computation is cheap against data already held, a view is the correct answer and a materialized copy is a maintenance liability.

Measured on a real session, the arithmetic of aligning spikes to an event and a window costs 0.13 to 1.72 s against trains already in memory, while a materialized copy of four alignments comes to 100.6% of the spike table itself (R43 §2). A wide trial table is 708 rows in 7.5 ms.

The test is therefore: does materializing change the *shape* of access, or only pre-compute a cheap step?

## 4. `analysis.spike_events`

Core keeps each spike on the clock of the probe that measured it, sorted unit-major. That layout answers "this unit's spikes" well and "every unit's spikes in this window" not at all, because a window across many clocks means nothing.

`analysis.spike_events` is core's spikes mapped onto the reference clock and bucketed by time, sorted by unit within each bucket, so that a time filter and a unit filter both prune (R30 §2).

| column | purpose |
|---|---|
| `session_id`, `unit_id`, `sorting_run_id`, `curation_id` | unit identity |
| `t_tick` | the spike, on the reference clock |
| `clock_id` | the reference clock |
| `time_bucket_tick` | the bucket this row lies in |

A row group lies inside one time bucket, so a window filter prunes at the row-group level. The bucket width cannot be recovered from the data and is therefore recorded in the producing run's parameters.

**Rows are not preserved.** A spike whose tick falls outside the region where the mapping is defined MUST be omitted rather than given an extrapolated value (R30 §4), so this table MAY hold fewer rows than core's. The count omitted MUST be recorded in the producing run's parameters, even when it is zero (R40 §2.3): a derived table one row short otherwise looks exactly like a complete one.

Measured on one session, a ten-second population window costs 0.025 s here against 7.7 s over a ragged per-unit representation.

## 5. Provenance of a materialization

Normative.

A materialization MUST record a `core.processing_runs` row and MUST name it from the resource's catalog entry (R31 §2). The run's parameters MUST carry any transform parameter that cannot be recovered from the output.

## 6. Withdrawn resources

Four resources proposed in v0.1 are withdrawn (R43 §2). They were specified before anything measured them:

| resource | disposition |
|---|---|
| `analysis.spikes_by_trial` | withdrawn; a table per (event, window) pair, and the alignment is cheap |
| `analysis.trials_wide` | withdrawn; 708 rows in 7.5 ms as a view |
| `analysis.unit_condition_rates` | withdrawn; its columns are a task's shape, not a format's |
| `analysis.good_units` | withdrawn; a filter, not a table |

The columns those tables carried — `condition_id`, `stimulus_id`, `block_id` — describe a particular task rather than the format, and belong in an extension (Part 09).

## 7. Views versus materialized products

Prefer a view where the query prunes and the result is small. Prefer a materialized product where the physical layout of core cannot serve the access pattern at all, which in practice means a different sort order or a different clock.

## 8. Promotion into core

An analysis resource becomes canonical only through an explicit revision of this specification. Promotion is a schema decision, not an operational one.

# Part 07 — Reference Implementation and Plan

Informative.

## 1. Scope

This part describes the reference implementation's shape and the phase plan. Nothing here constrains a conforming implementation.

## 2. Distribution layout

The reference implementation is three distributions with one command-line entry point.

| distribution | contents | depends on |
|---|---|---|
| `nwb-lake-reader` | manifest and resource resolution, tabular access | — |
| `nwb-lake-validator` | the checks of Part 05 | reader |
| `nwb-lake-writer` | source adapters, the recipe, the packet writer | validator |

The split is not cosmetic. The validator's correctness is pinned to a registry version while the reader's API is not, and the writer depends on the validator because commit is validate-then-rename (05 §6).

### 2.1 One command, three providers

`nwb-lake-reader` owns the `nwb-lake` console script. The other two register subcommands through an entry-point group. Two distributions declaring the same script name is a conflict in which the last installed wins silently.

### 2.2 Dependency discipline

Validation requires an embedded SQL engine, because the rules are SQL. Reading does not: a complete read path goes through the columnar library alone, so the SQL engine is an optional extra.

This is what Part 02 §5.2's ban on nested types exists to preserve — a native reader stays viable in a language without an embedded SQL engine.

## 3. Command line

```text
nwb-lake inspect <kind> <root>      what one source offers (05 §4.1)
nwb-lake init --source k=path ...   draft a recipe, flagging contested resources
nwb-lake import <recipe> --check    every problem, before any I/O (05 §3.5)
nwb-lake import <recipe> --strict   refuse anything an adapter worked around
nwb-lake import <recipe>            stages 2 to 7
nwb-lake verify <packet>            record what is true of external resources
nwb-lake prune <packet>             remove what the packet no longer names (03 §9.3)
```

## 4. Object model

| type | responsibility |
|---|---|
| `Packet` | resolve the catalog; hand back resources |
| `TableResource` | a table, as columnar batches or a scan |
| `ArrayResource` | an array, opened through the array library |
| `Validator` | run the generated and declared checks; return a report |
| `PacketWriter` | accumulate records; stage, validate, commit |

An adapter's return type is records, not a path. That is what lets adapters be tested without a filesystem and stops normalization decisions leaking into I/O code.

## 5. Phases

| phase | scope | state |
|---|---|---|
| 0 | hand-built fixture packet | complete |
| 1 | manifest and table reader | complete |
| 2 | validator | complete |
| 3 | source importer and recipe | complete |
| 4 | analysis materializations | complete; four of five resources withdrawn (06 §6) |
| 5 | dense arrays | complete, owned and referenced |
| 6 | release and version discipline | specified (03 §9); pruning implemented, amendment partial |
| 7 | Iceberg profile experiment | not started |

## 6. Testing

A conformance corpus holds one conforming packet and a set of variants, each with its expected finding recorded as data rather than as a test body. The corpus runs against the reference validator rather than reimplementing the checks.

Run it after changing the registry, the generator, or any rule.

## 7. Performance notes

These are properties of the reference implementation, not requirements.

- **Never convert a column to host objects inside a per-batch loop.** Every performance defect found in the reference writer has been this.
- **Read a large table in batches.** A 10⁸-row spike table decodes to many gigabytes if read whole.
- **Bound memory explicitly** where a job's working set is data-dependent, and give the SQL engine a spill directory: a memory limit without one bounds nothing.

## 4. Queries

Resource identifiers are dotted; a SQL engine registers them with underscores.

Units by quality, joined across core and an extension:

```sql
SELECT q.normalized_label, count(*) AS units,
       round(avg(m.isi_violations_ratio), 3) AS isi
FROM core_units u
JOIN aind_unit_qc_metrics m USING (session_id, unit_id, sorting_run_id, curation_id)
JOIN core_unit_quality_labels q USING (session_id, unit_id, sorting_run_id, curation_id)
```

## 5. Acceptance checklist

A packet of this shape is conforming when:

1. the catalog validates against the manifest schema;
2. every declared resource exists at its URI, or is declared external;
3. every packet-owned resource matches its recorded `sha256`;
4. Tier 1 and Tier 2 produce no error;
5. every table is in its declared physical order;
6. each declared extension registry exists and validates on its own terms.

# Part 09 — Metadata Minimalism and Extensions

Normative.

## 1. Scope

This part defines how much metadata core requires, where richer metadata belongs, and how an extension declares it.

## 2. Tiers

| tier | contents | location |
|---|---|---|
| 1 | packet-level facts | the catalog |
| 2 | facts needed to interpret, validate, join, or reproduce | core tables |
| 3 | domain-rich, lab-specific facts | an extension's tables |
| 4 | human-readable context | `docs/` sidecars |

## 3. Core inclusion rule

A field belongs in core only if common interpretation, validation, joining, or analysis would break without it.

A field SHOULD be in core when it is needed to interpret units, clocks, channels, arrays, or spike times; to validate a required relationship; to join tables; to filter or group a common analysis; to reproduce processing or curation; or to trace provenance.

A field SHOULD be in an extension or a sidecar when it is institutional, administrative, lab-specific, rarely queried, free-form, procedural but not required for analysis, or biologically rich but not required to interpret the recording.

## 4. Required minimum

A conforming packet requires only what is needed to identify, interpret, validate, query, and reproduce. The registry states the minimum per resource; this part does not restate it.

An import MUST NOT fail because optional extension metadata is absent.

## 5. Extensions

### 5.1 What an extension is

An extension is a registry document in the format of Part 02, in its own namespace (R17 §2). It declares tables, columns, references, and rules on exactly the same terms as core.

An extension needs no code. A registry document names its tables, Parquet files hold their rows, and neither imports anything of the reference implementation.

### 5.2 Namespacing

An extension's resource identifiers MUST be prefixed with its namespace: `dynamic_foraging.trials`, not `trials`. A namespace MUST NOT be `core`, `analysis`, or `nwb`.

### 5.3 Registration

A packet carrying extension resources MUST declare each namespace in the catalog with its version and the path to its registry document (04 §8).

A validator MUST check that a declared registry exists. It MUST NOT require an extension's schema in order to validate core.

### 5.4 Separate verdicts

An extension is validated on core's terms and its verdict is reported separately (R17 §4). A core failure MUST NOT be attributed to an extension, and an extension's failure MUST NOT invalidate core.

### 5.5 Independent versioning

An extension carries its own version, independent of `registry_version` (R17 §5).

## 6. Direction of reference

### 6.1 Core does not reference an extension

A core table MUST NOT declare a foreign key into an extension's table.

The reasons are separable verdicts (§5.4) and independent versioning (§5.5). "Interpretable when no extension is present" is *not* among them: a packet embeds its extension registries, so they are present whenever the resources are (R55 §5).

### 6.2 Core may name an extension

A core table MAY name an extension's resource through a `discriminator` column (Part 02 §8.3). `core.intervals.interval_kind` holds `dynamic_foraging.trials`, and a consumer resolves it by reading the kind, taking that resource's primary key from the registry, and joining.

**A discriminator names without depending.** It creates neither a shared verdict nor a version coupling, which is why it is the one mechanism core is allowed.

## 7. Promotion

A field moves from an extension into core through a revision of this specification, not by a writer deciding to emit it. Promotion is justified by §3's rule and by evidence that more than one producer needs it.

## 8. Anti-patterns

An implementation MUST NOT:

- make an extension's schema required in order to open core tables or arrays;
- hide analysis-critical metadata inside free-form JSON;
- use an object path as the only way to identify a resource;
- block an import because optional institutional metadata is incomplete;
- treat the catalog as a store for all metadata.

### 8.1 Untyped accretion

A table whose purpose is to hold arbitrary name-value pairs MUST NOT be added to core.

Nothing constrains the name, type, or meaning of what accretes in such a table, so two packets cannot be compared and neither can be checked. `core.trial_tags` was the one place this format permitted it and is withdrawn (R54 §2.3).

An extension needing a multi-valued attribute declares its own typed child table, as Part 02 §5.2 requires of everything else.
