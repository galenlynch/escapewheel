## 1. Scope

The generated v0.2 specification is the current authority, but it does not give an independent
implementer one coherent framework for locating that authority. The specification README acts as
an unnumbered normative preamble; Part 00 duplicates parts of it; exact declarations and
operational rules appear at several abstraction levels; and the word *layer* names two orthogonal
classifications.

This revision assigns authority by concern, makes Part 00 the specification framework, separates
abstraction level from packet content class, assigns every numbered part a subject and status, and
makes the specification README informational. It also distinguishes an authoritative working
candidate from an immutable release.

This revision changes the organization and interpretation of the specification, not the packet
contract. It does not select among the known disagreements about unit identity, resource
classification, requiredness, validation composition, registry conformance, executable rules,
adapter behavior, integrity, or publication artifacts.

## 2. Background

This section is informative.

### 2.1 The current framework has overlapping owners

The specification README contains the only top-level conformance, normative-language, and
normative-reference clauses. `combine.py` prepends it because it carries those clauses and the
version identifiers. A file normally used for navigation and publication guidance therefore acts
as normative prose outside the numbered parts.

The README and Part 00 §9 both classify parts. The README says that the specification has eleven
parts but lists only Parts 00–09. Part 00 includes Part 10 and the section-level exceptions for the
mixed Part 06, but R93 §3.6 says that a local part header wins if the two disagree. Three maintained
representations can therefore drift while a precedence rule still produces an answer.

Part 00 §1 says that the part defines no schema or file format. Part 00 nevertheless fixes a unit
key, reports exact registry counts, names columns and resources, prescribes reader behavior, gives
a measured join cost, and describes the first implementation. One copied measurement says that 33
of 35 core and analysis tables are session-scoped and that eight reach `core.sessions` without
carrying `session_id`; the baseline registry check reports 41 of 43 session-scoped tables and none
lacking the column. The count drift is evidence that the architecture is not the owner of the
declaration or its current measurements.

Part 02 §1 already demonstrates a narrower authority model. It makes
`registry/logical_schemas.json` normative for exact current declarations and
`registry/tables.md` an informative generated listing. Prose governs the declaration model and
semantics, the incorporated registry carries exact assignments, and the table listing is a
projection. File format alone determines none of those roles.

### 2.2 Two classifications currently share one name

Part 00 §§2.1–2.3 describe semantic, logical, and physical levels. Part 00 §3 uses *layer* for the
relationship of core, extension, analysis, and projection content to the packet. A core resource
has semantic meaning, a logical declaration, and a physical representation; an extension resource
can have the same three aspects. Neither classification refines the other.

The current wording obscures a third classification as well. A namespace assigns ownership
through dotted identifiers, while a resource kind distinguishes a table, array, media asset,
document, or view. Neither answers whether content is core, extension, derived analysis, or a
compatibility projection.

### 2.3 A working candidate and a release are different states

The tracked `RELEASE.json` is a prototype generated by `release.py`. At the baseline it records an
older commit, derives membership from Python constants and globs, includes several implementation
and lab-specific artifacts, and excludes the numbered specification sources. The repository
verifier does not establish it as a current authority.

This does not make the generated v0.2 specification optional. It shows that current authority and
publication state are independent: maintainers need one contract during development before a
later publication decision freezes exact members and bytes.

### 2.4 Existing decisions and impact

R93 §3.6 makes Part 00 list each part but gives a conflicting local header precedence. R111
§§3.1–3.2 defines the actors Part 00 already carries. R112 §3.1 and §3.4 places current
requirements in parts and preserves their section identifiers, and R113 §3.1 standardizes part
citations. This revision retains the actor and citation decisions and supersedes only R93 §3.6's
local-header precedence sentence.

At promotion, there were no other open proposals or drafts. The reverse-citation query over Part
00 §§1, 2, 2.1–2.3, 2.8, 3, 9, and 10 found 32 citations across nine sections. Incorporation has to
remeasure and read those citations, not merely establish that they resolve.

There are no published remote, external consumers, or released packets. No packet bytes or
implementation behavior change here, so packet migration is not required. The organizational
change is nevertheless material: a conflict becomes a candidate defect rather than a case where a
file-format or local-header precedence rule chooses a winner.

## 3. Decision

### 3.1 The current specification is an authoritative candidate

At any repository commit, the generated v0.2 numbered parts and every artifact that a numbered
part expressly incorporates **MUST** be the authoritative working specification at that commit.
An incorporated artifact participates only for the subject and extent the incorporating part
states.

The working specification **MUST** be called a **specification candidate** until a publication
decision identifies and freezes an exact release. *Authoritative* describes what governs current
development and conformance; *candidate* describes publication state. Candidate status **MUST NOT**
make the working specification optional.

The frozen proof-of-concept, proposals, drafts, accepted revisions, implementations, generators,
adapters, tests, examples, and developer documentation **MUST NOT** override the working
specification. Accepted revisions own the history and rationale for incorporated decisions. The
combined specification **MUST** be a reproducible convenience rendering of its inputs and
**MUST NOT** become a separately edited owner.

### 3.2 Authority is assigned by concern

Numbered prose **MUST** own terms, meanings, processing semantics, actor obligations,
conformance, and relationships that a structural declaration cannot express faithfully.

A machine-readable artifact **MUST** acquire normative authority only when a numbered part
expressly incorporates it. It **MUST** own only the exact structures or assignments for which that
part incorporates it. The incorporating prose **MUST** continue to own the vocabulary's meaning,
the semantics of declared fields, and every applicable processing or conformance rule not fully
expressed by the artifact.

Historical revisions **MUST** own rationale and provenance rather than current packet behavior.
Implementations and evidence **MUST NOT** acquire an independent normative subject by implementing
or testing a rule.

Normativity, representation, and production **MUST** remain independent properties. Prose is not
normative merely because it is prose; JSON is not authoritative merely because it is structured;
generated output is not informative merely because it is generated. The declared artifact role
and subject ownership determine authority.

### 3.3 Each fact has one owner and every other representation agrees

Each normative fact **MUST** have one owner. Another artifact that presents the same fact **MUST**
be one of:

1. a mechanically checked projection;
2. an explicitly informative explanation that links to its owner; or
3. an explicit consistency condition between different owners' subjects.

A disagreement between owners, an unfaithful projection, or an incorporated artifact that
violates its governing prose **MUST** make the candidate internally inconsistent. No general
prose-wins, data-wins, generated-wins, or local-file-wins rule **MAY** turn that disagreement into a
conforming release. An immutable specification release **MUST NOT** contain an unresolved
ownership conflict.

The working candidate remains the material to inspect while a known conflict is repaired. Known
misplaced and duplicate statements **MUST** be tracked outside the normative specification; their
inventory is evidence and work tracking, not an override.

### 3.4 Part 00 owns the specification framework

Part 00 **MUST** own:

- specification identity and candidate/release terminology;
- conformance targets and normative-language conventions;
- the normative-reference policy and complete normative bibliography;
- actors and the terms that resolve to them;
- normative, informative, and mixed status;
- artifact roles and the authority-by-concern rule;
- abstraction levels and their dependency direction;
- packet content classes as a separate classification;
- the subject owned by every numbered part; and
- stable citation and publication conventions.

Part 00 **MUST NOT** become the owner of exact keys, columns, registry counts, profile encodings,
performance measurements, implementation plans, or detailed lifecycle algorithms merely because
it summarizes the architecture. Where those statements remain during development, Part 00
**MUST** link to the actual owner or identify the summary as informative once the owner is settled.

### 3.5 Abstraction levels and packet content classes are separate axes

The specification **MUST** call semantic, logical, and physical classifications **abstraction
levels**:

- the semantic level defines what concepts mean, independently of representation and storage;
- the logical level defines concepts as computable resources and relationships, independently of
  a storage profile; and
- the physical level maps logical resources to stored bytes under a declared profile.

A lower abstraction level **MUST NOT** redefine a rule owned by the level above it. A physical
profile **MAY** map a logical resource to a storage technology and **MUST NOT** change that
resource's logical identity or semantic meaning. A workflow **MAY** describe how an actor satisfies
an owned invariant and **MUST NOT** restate a second version of that invariant.

The specification **MUST** call the architectural relationship of core, extension, derived
analysis, and compatibility-projection content to a packet its **packet content class**. Content
class **MUST** remain independent of abstraction level, namespace, and resource kind. A table and
an array may share a content class; a core table and an extension table share a resource kind but
not a content class.

**Namespace** **MUST** remain the dotted-identifier ownership mechanism. **Resource kind** **MUST**
distinguish tables, arrays, media, documents, and views. This clause does not require a packet to
serialize its content class and does not assign semantics to the current catalog `layer` field.

### 3.6 Each numbered part owns a stated subject

Part 00 **MUST** assign the following subjects to the numbered parts:

| part | owned subject |
|---|---|
| Part 00 | specification framework, authority, abstractions, part ownership and publication conventions |
| Part 01 | substrate-independent meanings of scientific and provenance concepts |
| Part 02 | logical resources, declarations, identities, references, and registry semantics |
| Part 03 | the portable physical mapping of logical resources to stored bytes |
| Part 04 | packet catalog structure, resource entries, and dataset-to-resource bindings |
| Part 05 | validation, import, writer lifecycle, reporting, and publication of a packet |
| Part 06 | analysis policy, examples, and explanation, subject to its mixed status in §3.7 |
| Part 07 | informative reference-implementation design and examples |
| Part 08 | informative executable packet example |
| Part 09 | extension boundaries, namespace ownership, extension declarations, and extension independence |
| Part 10 | informative performance measurements and rationale |

A part **MUST NOT** state a second version of a rule owned by another part. It **MAY** cite the
owner, or summarize the rule only when the summary is explicitly informative. An informative
section **MUST NOT** be the sole statement of an obligation.

Part 00 **MUST** assign the following normative status:

The status line at the head of each part **MUST** be a checked projection of Part 00. A
disagreement **MUST** make the candidate inconsistent; the local line **MUST NOT** take precedence.
This replaces the final sentence of R93 §3.6 and the corresponding current sentence in Part 00 §9.

A future release manifest **MAY** record numbered-part status, but that value **MUST** be a checked
projection of Part 00. The manifest **MUST NOT** become a second owner of numbered-part status.

### 3.8 The specification README is informational

The specification README **MUST** be an informational entry point. It **MAY** provide navigation,
candidate status, an architectural summary, build guidance, informative references, generated
status summaries, and links to owning artifacts. It **MUST NOT** be the sole statement of a
requirement or supply a normative preamble through its position in the combined rendering.

The current binding README material **MUST** be relocated by subject:

| current README subject | normative owner |
|---|---|
| purpose, applicability, conformance targets, actor summary, general composition of conformance, normative-language convention, document organization, and specification candidate identity | Part 00 |
| registry document structure, embedding, compatibility, `registry_version` semantics, and the temporary version hold | Part 02 |
| portable-profile identifier and the profile-dependent meaning of that identifier | Part 03 |
| packet catalog fields and the obligation to record applicable identifiers | Part 04 |
| validation and import consequences stated by the conformance summary | Part 05 |
| extension independence, namespace ownership, and extension-related reader or validator behavior | Part 09 |

A paragraph combining several subjects **MUST** be split among their owners. An existing detailed
clause **MUST** be cited rather than duplicated. A concise README summary **MAY** remain only when
it is identified as informative and links to the owner.

The combined-document generator **MAY** continue to place the README first for orientation. Its
ordering **MUST NOT** supply normative force, and the numbered part set **MUST** remain intelligible
without repository-specific developer documentation.

### 3.9 Part 00 owns the normative bibliography

Part 00 **MUST** carry the complete normative bibliography and the rule for how a normative
reference applies. The initial central bibliography **MUST** include RFC 2119, the Zarr v3 core
specification, the Apache Parquet format, and the Apache Arrow columnar format.

A subject-owning part whose requirements depend on an external specification **MUST** cite the
corresponding Part 00 bibliography entry. It **MUST NOT** maintain a second normative bibliography.
Centralizing the reference **MUST NOT** move the subject requirement into Part 00.

The informational README **MAY** retain informative references and links to Part 00's normative
bibliography. It **MUST NOT** contain a normative-reference section of its own.

## 4. What this does not change

- No packet field, resource, table, column, key, reference, rule, vocabulary, physical encoding,
  validation result, reader API, writer behavior, or adapter contract changes. Existing packets do
  not require migration or regeneration.
- No new registry, meta-schema, JSON Schema, rule language, or release manifest is incorporated.
  Part 02's existing incorporation of the core logical registry remains in force.
- The normative status assigned to each part and Part 06 section remains unchanged; only ownership
  and checking of that status change.
- The draft does not decide unit identity, resource requiredness, serialized content
  classification, `layer`, `canonical`, lineage, packet registry binding, validity composition,
  recipe arbitration, adapter capabilities, integrity, codecs, or final version identifiers.
- The draft does not define final release-manifest membership, roles, hashes, identifiers, or
  publication tooling.

the README, a local status header, a revision, or an implementation as an independent precedence
source. It preserves packet shape and interpretation. Incorporation requires document relocation,
generation, citation review, and framework checks, not packet migration.

## 6. Conformance and implementation evidence

Incorporation adds a focused specification-framework checker. It parses Part 00's part-ownership
and status tables, every local part status, the placement of the normative bibliography, the
informational README, and the combined rendering.

Positive cases establish that:

- Parts 00–10 each appear exactly once;
- every local status agrees with Part 00, including Part 06's mixed-section exceptions;
- Part 00 contains the central normative bibliography;
- the README contains neither a normative-reference section nor a normative-keyword obligation;
  and
- the combined specification is a reproducible projection that includes Part 00.

Negative cases cover a missing or duplicate part row, an unknown part, a conflicting local status,
a missing or conflicting mixed-section exception, a normative-reference section or normative
keyword introduced into the README, a missing central bibliography, and a combined rendering that
is stale or omits Part 00.

Keyword scanning cannot prove that informative prose contains no unique rule. A human relocation
inventory therefore gives every current README paragraph one disposition: moved to an owner,
replaced by a citation, retained as an informative summary, or removed as a duplicate. The
incorporation evidence records that inventory and the framework check's positive and negative
tests.

Before acceptance appraisal, the impact query over Part 00 §§1, 2, 2.1–2.3, 2.8, 3, 9, and 10 is
rerun against the current baseline. Incorporation reads every citer and separately sweeps every
destination that receives README text. The evidence manifest records that no registry declaration,
packet schema, fixture, implementation behavior, or version identifier changed.

The mechanical closure commands are the stage and citation checks, the evidence checker, the
revision ledger, the heading check, the combined-specification check, and the complete repository
verifier. Their passing establishes structural and generated agreement; the relocation inventory
and citation reading establish semantic placement.

## 7. Pre-acceptance blockers

This section records the current appraisal state; it is informative and adds no Decision clause.
The draft remains blocked while the controlled-reorganization work is again a proposal. Its first
acceptance appraisal found that repository-maintenance procedure and historical-revision mechanics
had been assigned to normative Part 00, and that the ledger's reverse-citation check made current
authoritative owners depend on their change records. The revised proposal assigns maintenance to
`revisions/CONTRIBUTING.md`, moves one-way ledger traceability under `revisions/`, and leaves the
completed historical audit as non-gating evidence. It also splits removal of historical and
misplaced maintenance material from authoritative artifacts into a dependent proposal because
registry provenance and `since` have separate compatibility effects and Part 00 §§10.1–10.4 need
clause-level dispositions. Neither proposal is yet a dependency this draft can carry into accepted
history.

After that prerequisite lands, the following work occurs in order:

1. **Define the exact structural landing.** Revise `Amends` and the consequence inventory with the
   resulting Part 00 outline. Give every existing Part 00 section and every current README
   paragraph an old location, disposition, new location, semantic effect, and governing Decision
   clause. Apply the accepted boundary between packet-specification content and repository
   maintenance instead of relocating process mechanics within Part 00. Name the exact receiving
   sections in Parts 02, 03, 04, 05, and 09 rather than only their subjects.
2. **Identify and bootstrap affected headings.** Enumerate every existing numbered section that is
   a source or destination of relocated prose or whose heading, level, number, or order will
   change. Give each such heading a canonical anchor in a separate metadata-only commit before the
   structural incorporation. The bootstrap changes no heading text, numbering, order, prose,
   normativity, or meaning. The structural change gives every new destination an anchor and records
   an alias only where the crosswalk declares one primary successor under the accepted process
   rule.
3. **Refresh the draft after the bootstrap.** Replace `Based on` with the full commit hash that
   contains the accepted process rule, completed authoritative-source maintenance and history
   cleanup, and required anchor bootstrap. Add both accepted prerequisite revisions to `Depends on`,
   rerun every count and impact query, re-inventory overlapping work, and update stale evidence. The
   earlier count of 32
   citations into affected Part 00 sections is historical promotion evidence, not the acceptance
   population.
4. **Complete current traceability.** List and read every affected live citation and update it to
   the destination's current number and anchor. Convert every affected `applied.toml` and revision
   evidence target to its anchor form, update the heading record, and regenerate the combined
   specification and human-facing authority summaries. Current authoritative owners do not cite
   accepted revisions merely to corroborate the ledger. Any retained historical-citation audit is
   process evidence over immutable revision records, not specification content.
5. **Make the framework obligations decidable.** Bind specification-maintenance and publication
   obligations to a named actor or a testable artifact property. Name the framework check and its
   positive and negative tests for Part 00 ownership and status, local status projections, README
   informativity, normative-reference placement, and combined-rendering reproducibility. Keep that
   checker distinct from the controlled-reorganization process checks on anchors and revision
   history.
6. **Repeat the complete pre-acceptance appraisal.** Re-run the freshness, decision, feasibility,
   compatibility, traceability, evidence, citation, repointing, and repository gates against the
   post-bootstrap baseline. Commit that exact appraised draft before requesting acceptance
   authorization.

These are blockers to accepting and incorporating this draft, not additional normative decisions.
They preserve §3 while making its consequences exact and reviewable.
